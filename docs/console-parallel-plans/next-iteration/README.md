## 四个 agent 的执行顺序

协调 agent 00 占一个名额，同时最多运行三个开发 agent。

1. **契约阶段**：02 核对权威关系/服务端能力，04 建立旧 Web 等价清单，05 调查目标部署和升级夹具。00 冻结首版生命周期契约。01 可研究现有 OIDC 客户端，但认证核心尚不开放并行编辑。
2. **认证阶段**：01 独占 Console 认证核心并接入 OIDC，02 在 OtterIO 独立分支实现必要协议，04 在独立夹具中准备 OIDC/权限验收。05 未完成部分排队或使用空出的名额。
3. **功能阶段**：认证核心归还 00。03-user、03-group、03-service-account 在契约稳定后最多三个并行；只编辑各自新增模块，共享 dispatcher/UI 由 00 顺序接入。若 01 未完成，它保留一席，IAM 子任务依序排队。
4. **组合阶段**：04 对集成版本做功能/权限/browser-off 验收，05 做真实 IdP、部署、长期稳定性及发行配对，06 准备删除 PR 的依赖与回归清单。00 修复组合缺陷并重跑受影响项目。
5. **退休阶段**：发行认证及通知条件满足后，06 交付默认关闭；约定回退窗口结束后再交付删除。04/05 分别复验核心协议和发行/升级。阶段不能靠并发压缩外部通知窗口。

某任务等待共享文件时，继续做专属测试、协议调查或夹具；不得在另一个负责人窗口内修改同一文件。以上是逻辑阶段，不是工期承诺。

## 迭代与交接

每个 agent 在独立 worktree/分支中开发，不切换他人的 checkout。本地准备和可回退修改可推进；发布、部署、合并按当时已获得的授权和仓库流程处理。

每轮只交付一个可独立审查的行为变化：先失败用例或准确能力缺口，再实现，再相关 race/权限/真实协议检查，最后提交交接。避免把登录、刷新、所有 IAM 和删除合成一个 PR。任务状态按 `unclaimed → active → review → integrated → verified` 更新；等待依赖记为 `blocked` 并列明解除条件，不能把 review 当成已集成。

交接必须包含：task ID、仓库/worktree/分支、源提交、变更范围、共享窗口归还、接口变化、实际命令与结果、失败/skip、真实程序摘要和 harness 来源、剩余风险、接入顺序。凭据、token、登录码、临时密钥及原始认证响应不得进入报告。

协调者集成后重新构建并验证受影响组合；单 agent 的历史通过结果不能认证新的集成提交。出现接口争议由 00 更新 contracts.md，通知依赖任务后继续；禁止 agent 自行复制出第二套认证或撤销机制。
