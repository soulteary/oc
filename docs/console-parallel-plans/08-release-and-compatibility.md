# 正式发行与真实版本验收

负责人角色：发行验收 agent。预计工作量：6–10 人日。估算含实现、审查、CI 修复与验收，不是日期承诺。

## 启动条件

基线工作立即开始；完整替代结论依赖 02、04、05、06、07 集成。

## 开发内容

- 核实最新 OC/OtterIO 正式版、源提交、校验和和镜像 digest；源码、补丁服务器和实际发行组合分别记录。
- 当前正式 OC 早于原生身份能力；先评估实际服务器所需 self-credentials/条件创建/轮换/绑定能力，把缺口落实为服务端正式交付任务。
- 构建受支持功能/身份/版本矩阵；真实旧 Web 关闭下验收 S3、Admin、STS、健康检查、metrics 和所有承诺支持场景。
- 整理 OC 与服务端的发布候选、兼容说明和打包/镜像校验；实际发布按当前用户授权和发布流程执行，准备不等于正式发布。
- 原生执行目标平台和 amd64/arm64 容器，不能以交叉编译替代运行验收；不支持的平台需正式调整支持契约。
- 真实升级、凭据/偏好/配置保留、同版本 UI 回退与重新关闭演练。服务端降级的数据/生命周期引用兼容单独验证。
- 保留失败证据，报告包含版本、二进制 hash、脚本版本、平台和配置。各工作包输出独立报告，本任务汇总而不是覆盖失败。

## 文件和职责边界

拥有：发行脚本/工作流、兼容清单、现有发行 Compose pin、正式配对与 Compose 验收脚本、统一发行报告。

其他任务不修改 `.github/workflows` 和发布 pin；需要 CI job 接入时提交本任务处理。02 的服务端协议 PR 与发行工作分开。

## 验收条件

- 每项能力对应实际可安装版本与权限负例；没有能力头时拒绝/明确降级。
- 原生平台与两种容器架构的执行、版本/归档字节检查及升级回退报告。
- 完整承诺范围在旧 Web 关闭时通过；OIDC、临时凭据、IAM、配置、对象传输的交互负例。
- 形成允许试部署/允许默认关闭/允许删除三种不同结论，不用一份局部通过报告替代全部门槛。

## PR 和合并顺序

版本差异/基线 PR → 必要发布管线/兼容 PR → 完整配对与升级验收 PR；贯穿全程，不等待全部代码写完才开始。

## 认领和交付规则

开始时读取本目录 README 与契约计划，在独立分支和独立 worktree 开发，确认依赖 PR 的实际合并状态。任务文件不是创建、推送或修改其他 agent 分支的授权；按当前用户授权完成本任务的开发和 PR。

只修改本计划拥有的文件。共享文件的改动整理为明确的接入补丁，交给指定拥有者合并；需要提前调整接口时，先更新契约并通知受影响任务，不自行改变已冻结语义。测试使用临时账户和存储，避免实际用户配置或数据。

每个 PR 写明问题、最终行为、验证结果、版本与限制。失败记录与未知结果须保留，不自动重放身份变更，不以管理员代查/代操作普通用户资源。文档和测试证据只声明实际运行过的组合。

交付时提供提交/PR、已完成验收、未解决项和接入要求。共享验收报告、主迁移文档、主前端文件与发布 pin 统一由集成/发行拥有者更新，避免并行覆盖。
